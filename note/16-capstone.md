# 卒業課題 — AI 協働で本番化せよ

## 1. 課題の目的

この課題では、AI にコードを書かせること自体は評価しません。あなたが仕様を決め、
生成された変更をレビューし、テストと実行結果を根拠に受理または差し戻しを判断する
ことを評価します。

「AI が作ったので動くはず」ではなく、**その変更を本番に出してよいと言えるか**を
自分の言葉で説明してください。

## 2. テーマを 1 つ選ぶ

| テーマ | 主な変更箇所 | レビューで必ず扱う観点 |
|--------|--------------|------------------------|
| 書籍の説明文 | `books.ts`、`store.ts`、`api.ts`、UI | backend/frontend の型と入力検証の同期 |
| ページネーション | `listBooks`、API、`api.ts`、UI | `total`、page/limit の境界、既存クライアントとの互換性 |
| D1 永続化 | `wrangler.jsonc`、`store.ts` または DB 層 | SQL injection、transaction、NULL、snake_case の変換 |
| 貸出履歴 | REST ルート、型、DB/ストア、UI | 履歴を別リソースにする理由、状態変更との整合性 |
| テスト追加 | `store.ts` のテスト、テスト設定 | 正常系だけでなく空入力・境界値・状態遷移 |

既存 README の学習課題にないテーマを選ぶ場合は、対象範囲と完了条件を事前に講師へ
確認してください。

## 3. 進め方

### 3.1 仕様を先に書く

次の項目を含む短い仕様を作ります。AI への最初のプロンプトは、この仕様を渡す形に
してください。

- 利用者ができることと、できないこと
- 変更する API・型・画面
- 成功時と失敗時の振る舞い
- 境界条件 (空、最大値、重複、同時実行など)
- 完了を判定するコマンドまたは手動確認

### 3.2 AI に実装させる

AI にはリポジトリの関連ファイル、現在の制約、仕様、検証方法を伝えます。最初から
「全部直して」と依頼せず、設計案と変更ファイルの一覧を先に出させてください。

記録するもの:

- 使用したプロンプト
- AI が提案した設計と変更ファイル
- 採用しなかった提案と、その理由

### 3.3 PR としてレビューする

生成された差分を、次の表の形式でレビューします。

| 重要度 | ファイル・行 | 指摘 | 根拠 | 対応 |
|--------|--------------|------|------|------|
| high / medium / low | `path:line` | 何が問題か | 仕様・型・実行結果 | 修正 / 許容 / 差し戻し |

最低 1 件は、AI のコードが動くかどうかだけでは見つからない指摘を入れてください。
例: `unknown` を `any` に変えた、HTTP 400 を 200 で返す、空データで `NaN` になる、
SQL の列名を文字列連結している、CORS と credentials が矛盾している、など。

### 3.4 検証して判定する

レビュー後に自分で修正を加え、次を実行します。テーマに不要な項目は理由を記録して
省略して構いません。

```bash
npm run typecheck
npm run lint
npm run build
```

API の変更は `curl -i`、UI の変更はブラウザの Network/Console、データ変更は空データ・
重複・再起動などの境界ケースも確認します。最後に PR を `受理`、`条件付き受理`、
`差し戻し` のいずれかで判定し、理由を書きます。

## 4. レビューレポートのテンプレート

```md
# 卒業課題レビュー

## 選んだテーマ

## 仕様と完了条件

## AI に渡した指示

## AI の変更概要

## レビュー指摘

| 重要度 | 場所 | 指摘 | 根拠 | 対応 |
|--------|------|------|------|------|

## 実行した検証

## 最終判定

## 振り返り
```

## 5. D1 を選ぶ場合の追加チェックリスト

D1 化を選んだ場合は、次をすべて確認してください。

- `sort` の値が allowlist にないとき、SQL の文字列連結に入らない
- 検索値はプレースホルダで bind されている
- `status`、`rating`、`published_year` の制約がアプリ側と DB 側で矛盾しない
- `borrower` の `NULL` と空文字を区別できる
- DB の `snake_case` を `Book` の camelCase に変換している
- リセットの DELETE と INSERT が途中状態を外部に見せない
- シード投入と本番データ削除の操作が分離されている
- CORS、`NEXT_PUBLIC_API_URL`、wrangler の binding が環境ごとに一致する

## 6. 評価の観点

| 観点 | 目安 |
|------|------|
| 仕様化 | 完了条件と境界条件が具体的か |
| レビュー | 問題の発見に根拠があり、重要度を判断できているか |
| 検証 | 実行結果・型・テストを使って判断を裏付けているか |
| 改修 | 最小の変更で問題を直し、別の回帰を生んでいないか |
| 説明 | AI の提案を採用・却下した理由を説明できるか |

コードの行数や AI に書かせた量は評価しません。コードが動くことは最低条件ですが、
最終的な評価対象は「そのコードを信頼してよいかを判断する力」です。

### 講師向けの運用

同じテーマでもレビュー力を測りたい場合は、AI の PR に 1〜3 個の既知の欠陥を混ぜて
配布できます。欠陥は授業で扱った概念に限定します。たとえばバリデーションの
条件付き必須を削る、`localeCompare` の比較対象を取り違える、`Record<BookStatus, ...>`
を `Record<string, ...>` に緩める、D1 の `ORDER BY` を文字列連結する、などです。
欠陥を見つけるだけでなく、再現手順と修正後の検証結果まで提出させます。
